BARISTA PLATFORM — WHAT EACH SERVICE DOES & HOW THEY CONNECT
═══════════════════════════════════════════════════════════════

THINK OF IT LIKE A COMPANY BUILDING:
─────────────────────────────────────
  Kafka     = Post Room    (receives & routes messages)
  MongoDB   = Filing Room  (stores documents/records)
  Supabase  = Reception    (frontend API + database)
  LibreFS   = Storage Room (stores files/objects)
  Longhorn  = Hard Drives  (disk storage for all pods)
  Strimzi   = Post Manager (manages the post room)

SUPABASE — WHAT IS IT EXACTLY?
═══════════════════════════════════════════════════════════════

Supabase is NOT one thing — it's 6 services in one:

┌─────────────────────────────────────────────────────────────┐
│  SUPABASE COMPONENTS                                        │
│                                                             │
│  PostgreSQL (CNPG)  → main database (stores app data)       │
│  PostgREST          → auto REST API from postgres tables    │
│  Auth Service       → login/logout/JWT tokens               │
│  Realtime           → websocket live updates                │
│  Storage            → file uploads (uses LibreFS/S3)        │
│  Studio             → web UI to manage everything           │
│  Kong               → API gateway (routes all requests)     │
│                                                             │
│  Think of it as:                                            │
│  "Give me a database and I'll auto-generate                 │
│   an API, auth, file storage and UI for it"                 │
└─────────────────────────────────────────────────────────────┘


HOW LIBREFS AND LONGHORN DIFFER
═══════════════════════════════════════════════════════════════

LONGHORN                          LIBREFS
────────────────────────          ────────────────────────
Block storage                     Object storage
like a hard drive                 like a file cabinet
mounted inside pod                accessed via HTTP/S3 API
used by databases                 used for files/backups
(Kafka, MongoDB, Postgres)        (images, logs, backups)
kubectl get pvc                   curl http://librefs:9000


COMPLETE DATA FLOW EXAMPLE
═══════════════════════════════════════════════════════════════

1. App sends event to Kafka (port 9092)
        │
        ▼
2. Kafka stores message in broker pod
   (data saved on Longhorn PVC - 20Gi)
        │
        ▼
3. HERCULES consumes from Kafka
        │
        ├──▶ saves to MongoDB (documents)
        │    (data on Longhorn PVC - 50Gi)
        │
        └──▶ Supabase REST API reads MongoDB/Postgres
                  │
                  ├──▶ file uploads → LibreFS (S3)
                  │
                  └──▶ UI via Supabase Studio




Bottom line — each service has one job:

Kafka → move data between apps
MongoDB → store document data
Supabase → provide API + auth + database for frontend apps
LibreFS → store files (like S3)
Longhorn → provide disk to all pods (invisible layer)

SIMPLE RULE
═══════════════════════════════════════════════════════════════

Complex stateful apps  →  need an Operator
(Kafka, MongoDB,           (operator handles
 PostgreSQL)                upgrades, HA, backups)

Simple stateless apps  →  just Helm chart
(Supabase UI, Kafka UI,    (no special lifecycle
 LibreFS)                   management needed)
