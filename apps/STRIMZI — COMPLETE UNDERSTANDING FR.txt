  FIRST — UNDERSTAND KUBERNETES BASICS
  ══════════════════════════════════════

  Normal World (Server):          Kubernetes World:
  ──────────────────────          ─────────────────
  Install app on server     →     Deploy app as Pod
  Config in /etc/app/       →     Config in ConfigMap/Secret
  systemctl start app       →     kubectl apply -f app.yaml
  app runs on port 8080     →     Service exposes the port
  multiple servers          →     multiple Pods
  load balancer             →     Service (ClusterIP/NodePort)


  WHAT IS AN OPERATOR?
  ══════════════════════════════════════════════════════════════

  Normal Way (you manage everything manually):
  ┌────────────────────────────────────────────┐
  │  You SSH → install kafka → edit config     │
  │  You SSH → start kafka → check status      │
  │  You SSH → upgrade kafka → restart         │
  │  You SSH → add broker → update config      │
  │  (lots of manual work!)                    │
  └────────────────────────────────────────────┘

  Operator Way (operator manages everything):
  ┌────────────────────────────────────────────┐
  │  You write yaml → kubectl apply            │
  │  Operator reads yaml                       │
  │  Operator does everything automatically:   │
  │  → installs kafka                          │
  │  → creates config                          │
  │  → starts brokers                          │
  │  → handles upgrades                        │
  │  → handles failures/restarts               │
  │  → scales up/down                          │
  └────────────────────────────────────────────┘

  Strimzi IS the Kafka Operator for Kubernetes!


  HOW STRIMZI IS DEPLOYED (your mat_ansible flow)
  ══════════════════════════════════════════════════════════════

  STEP 1 — Ansible deploys Strimzi Operator
  ──────────────────────────────────────────
  mat_ansible/roles/kubernetes/streaming/kafka
       │
       │  installs:
       ▼
  strimzi-cluster-operator pod (blp25082080)
  → this is just a pod watching for Kafka yamls
  → does nothing until you give it a Kafka CR


  STEP 2 — Ansible applies Kafka CR (Custom Resource)
  ─────────────────────────────────────────────────────
  A CR (Custom Resource) is just a yaml that describes
  what you WANT. Strimzi reads it and makes it happen.

  Example Kafka CR (simplified):
  ┌────────────────────────────────────────────────────┐
  │  apiVersion: kafka.strimzi.io/v1beta2              │
  │  kind: Kafka                          ← type       │
  │  metadata:                                         │
  │    name: barista-kafka-cluster        ← your name  │
  │    namespace: kafka                                │
  │  spec:                                             │
  │    kafka:                                          │
  │      replicas: 3                      ← 3 brokers  │
  │      listeners:                                    │
  │        - name: internal                            │
  │          port: 9092                                │
  │          type: internal                            │
  │          tls: false                                │
  │        - name: external                            │
  │          port: 9094                                │
  │          type: nodeport               ← nodeport   │
  │          tls: false                                │
  │      storage:                                      │
  │        type: persistent-claim                      │
  │        size: 100Gi                                 │
  │    zookeeper:                                      │
  │      replicas: 3  (or KRaft mode - no zookeeper)  │
  └────────────────────────────────────────────────────┘

  STEP 3 — Strimzi reads CR and creates everything
  ─────────────────────────────────────────────────
  Strimzi Operator
       │
       ├──▶ creates broker pods (pool-0, pool-1, pool-2)
       ├──▶ creates controller pods (pool-3, pool-4, pool-5)
       ├──▶ creates entity-operator pod
       ├──▶ creates services (ClusterIP, NodePort)
       ├──▶ generates /tmp/strimzi.properties
       ├──▶ creates secrets (TLS certs, passwords)
       └──▶ creates configmaps

  │    namespace: kafka                        │

┌─────────────────────────────────────────────────────────────┐

┌─────────────────────────────────────────────────────────────┐
│  AFFINITY — WHERE PODS CAN RUN                              │
│  ─────────────────────────────                              │
│                                                             │
│  nodeAffinity:                                              │
│    requiredDuringScheduling...                              │
│      matchExpressions:                                      │
│        key: {{ kafka_node_label_key }}                      │
│        operator: In                                         │
│        values: {{ kafka_node_label_value }}                 │
│                                                             │
│  Translation:                                               │
│  "Only schedule controller pods on nodes                    │
│   that have label kafka_node_label_key=value"               │
│                                                             │

│  node label: role=kafka                                     │
│  → only blp25082081, blp25082084, blp25082087               │
│    get controller pods (not master node)                    │
│                                                             │
│  podAntiAffinity:                                           │
│    requiredDuringScheduling...                              │
│      topologyKey: {{ kafka_topology_key }}                  │
│                                                             │
│  Translation:                                               │
│  "Never put 2 controller pods on SAME node"                 │
│  → pool-3 on blp25082087                                    │
│  → pool-4 on blp25082081   ← each on different node ✅      │
│  → pool-5 on blp25082084                                    │
│  (high availability!)                                       │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  TOPOLOGY SPREAD CONSTRAINTS                                │
│  ───────────────────────────                                │
│  maxSkew: {{ kafka_topology_max_skew }}                     │
│         → usually 1                                         │
│  whenUnsatisfiable: DoNotSchedule                           │
│                                                             │
│  Translation:                                               │
│  "Spread pods evenly across nodes"                          │
│  "If can't spread evenly → don't schedule at all"           │
│                                                             │
│  Example (3 controllers, 3 nodes):                          │
│  node1: 1 controller ✅                                     │
│  node2: 1 controller ✅                                     │
│  node3: 1 controller ✅  → perfectly balanced               │
│                                                             │
│  If node3 is down:                                          │
│  node1: 1 controller                                        │
│  node2: 1 controller                                        │
│  node3: 0             → skew=1, ok                          │
│  node1: 2 controllers → skew=2, DoNotSchedule! ❌           │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│  STORAGE                                                    │
│  ───────                                                    │
│  type: persistent-claim                                     │
│         → uses PVC (PersistentVolumeClaim)                  │
│         → data survives pod restarts ✅                     │
│  size: {{ kafka_controller_storage_size }}                  │
│         → e.g. 100Gi                                        │
│  class: {{ kafka_storage_class }}                           │
│         → e.g. longhorn (your storage class)                │

HOW TO CHECK WHAT'S DEPLOYED
═══════════════════════════════════════════════════════════════

# see all node pools
kubectl get kafkanodepool -n kafka

# see controller pool details
kubectl describe kafkanodepool \
  barista-kafka-cluster-controller-pool -n kafka

# see actual values (replicas, resources etc)
kubectl get kafkanodepool \
  barista-kafka-cluster-controller-pool \
  -n kafka -o yaml

# check which nodes controllers are on
kubectl get pods -n kafka -o wide | grep controller

# check resources allocated
kubectl describe pod \
  barista-kafka-cluster-controller-pool-3 \
  -n kafka | grep -A5 "Requests\|Limits"

# check storage (PVC)
kubectl get pvc -n kafka | grep controller

# check node labels
kubectl get nodes --show-labels | grep kafka



HOW TO UPDATE CONFIG
═══════════════════════════════════════════════════════════════

Option 1 — via Ansible (recommended):
──────────────────────────────────────
1. update variable in inventory/vars file
   e.g. kafka_controller_requests_memory: 4Gi → 8Gi

2. run ansible playbook
   ansible-playbook playbook/kubernetes/kafka.yaml \
     -i inventories/barista/pre_prod/hosts \
     --vault-password-file .vault

3. Ansible renders template with new values
4. kubectl apply sends to Kubernetes
5. Strimzi does rolling restart automatically


Option 2 — direct kubectl edit (quick fix):
────────────────────────────────────────────
kubectl edit kafkanodepool \
  barista-kafka-cluster-controller-pool -n kafka

→ change value directly
→ save → Strimzi applies change automatically
→ BUT this will be overwritten next Ansible run!
   so always update Ansible vars too
